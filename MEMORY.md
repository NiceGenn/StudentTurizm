# Принятые решения

Короткие записи о том, почему сделано именно так. Помогают не переоткрывать
обсуждённое и отвечать на вопросы на защите.

## Django, а не PHP или React + API

Готовая админка закрывает роль контент-менеджера без единой строки CRUD-кода.
ORM снимает ручной SQL, `django.contrib.auth` даёт роли и регистрацию,
встроенный `i18n` — мультиязычность. На PHP это писалось бы вручную; связка
React + API означала бы два стека сразу и заметно больший риск не собрать
работающий продукт.

## SQLite по умолчанию, PostgreSQL по переменной окружения

ТЗ называет целевой СУБД PostgreSQL, но требовать её для запуска — значит
поставить барьер на первом шаге. Выбор вынесен в `DB_ENGINE`: код одинаков,
миграции одни и те же, переход занимает три переменные окружения.

## Переводы дублирующими полями, а не отдельной таблицей

`title`, `title_en`, `title_zh` в одной строке читаются глазами, не требуют
JOIN-ов и понятны контент-менеджеру в админке. `django-modeltranslation` и
таблица переводов на текущем объёме не окупаются; при росте числа языков
решение меняется без переписывания представлений — достаточно поменять
`TranslatedFieldsMixin.tr()`.

## Статусы объектов как отдельное поле, а не текст в описании

Главная содержательная проблема темы — устаревшие сведения (горнолыжная база
в Натальино описана как работающая в источниках, но заморожена; канатная
дорога ещё строится). Поле `status` позволяет показать это меткой на карточке,
предупреждением на странице и запретом на включение в маршруты. Валидатор
`tools/check_data.py` требует пояснение `fact_note` для всего, что не
`active`.

## Признак `in_district` вместо исключения объектов

Муравьёвский парк и канатная дорога полезны как контекст, но находятся вне
округа. Вместо того чтобы либо врать, либо молчать, они помечены
`in_district = false`, выводятся отдельным блоком и не попадают в маршруты.
Ради этого `Attraction.village` сделан необязательным.

## Контент в JSON, а не в фикстурах Django

`data/*.json` читается и правится человеком, проверяется отдельным
скриптом до попадания в базу и не завязан на внутренний формат Django.
`seed_demo` идемпотентен: ищет по `slug` и обновляет.

## Даты событий как «месяц + день», а не абсолютные

Демонстрационный календарь с фиксированными датами устаревает через сезон.
`seed_demo` подставляет ближайшее наступление даты, поэтому на защите в любой
момент видны предстоящие события.

## Рейтинг вычисляется, а не хранится

`Avg` по одобренным отзывам в `AttractionQuerySet.with_rating()`. Хранимое
поле пришлось бы пересчитывать при каждом изменении статуса модерации и
рано или поздно разошлось бы с фактическим значением.

## Leaflet + OpenStreetMap, а не Яндекс.Карты

Не нужны ключ, регистрация и привязка домена — только атрибуция (ODbL).
Для учебного проекта это на порядок меньше препятствий.

## Заглушки вместо фотографий

Права на снимки объектов не оформлялись, поэтому в репозитории фотографий
нет. `seed_demo` рисует абстрактный пейзаж в цвете категории через Pillow:
интерфейс выглядит наполненным, и никто не выдаёт чужие снимки за свои.
Настоящие фотографии загружаются через панель управления.

## Bootstrap и Leaflet — в репозитории

Библиотеки лежат в `sources/static/vendor/` и подключаются оттуда: на защите
не должно быть зависимости от CDN. Настройка `VENDOR_LOCAL` проверяет наличие
файлов, поэтому при их удалении шаблоны сами вернутся к CDN, а обновить
версии можно скриптом `tools/vendor_assets.sh`. Тайлы карты всё равно
требуют интернета — это ограничение любого решения на онлайн-картах.
